Kalshi Market Pipeline & Lakehouse

data pipeline · Python, Databricks · Aug 2026 – present
In progress. The source repository is private, so there is no public link; I’m happy to walk through the code in an interview.

Problem

Prediction-market prices are supposed to be probabilities: an event trading at 70¢ should happen about 70% of the time. Checking that (market calibration) needs a complete, clean record of every market and every trade. Kalshi only serves that data through a rate-limited API, and a pipeline that drops or double-counts trades would quietly skew the answer.

Approach

Ingestion runs on my laptop, on a launchd schedule, so Kalshi credentials never leave it; the cloud only ever gets data. Hourly jobs pull trades and markets through an async client that shares Kalshi’s read and write rate limits across every running job. Each job writes immutable, compressed “part” files, and a sync step uploads each finished part to Databricks exactly once. There, COPY INTO loads each file once into raw Delta tables, incremental MERGEs build deduplicated Silver tables plus a quarantine for bad rows, and Gold tables measure calibration at fixed horizons before each market closes.

Under the hood: asyncio + aiohttp with RSA-PSS request signing, a file-locked token bucket per account (read and write) shared across processes, and full-jitter retries with a typed error hierarchy. Every job starts through one bootstrap that validates settings and takes a job lock, with exit codes as the contract to the scheduler. Bronze parts are gzip JSONL, fsynced and atomically renamed before any checkpoint moves, so a crash can cause duplicates but never gaps. Silver advances a per-entity watermark only after every idempotent step succeeds, so a retried batch changes nothing.

Progress is never claimed before data is durable. A job writes into a hidden in-progress file; seal() closes the gzip stream, fsyncs, renames it to its final name, and fsyncs the directory, and only then does a checkpoint move. A crash leaves at worst an unsealed file whose data was never checkpointed, so the rerun re-fetches it: duplicates are acceptable, gaps are not, and Silver dedupes.

Bronze files are immutable. The first version appended to one file per day, which forced size checks during sync and once grew a single markets file to 43 GB raw. Sealed parts are never touched again, so sync uploads each one once and Databricks’ COPY INTO loads each one once, with no ledger of my own. A database was considered and rejected, including SmallDB: Bronze is written and read sequentially in full, with no key lookups for an LSM tree to speed up.

One rate limit, many processes. Kalshi enforces separate read and write limits per account, so the token bucket lives in a file-locked state file that every job shares. Reconfiguring from the account’s live limits clamps the tokens instead of refilling them, because another process may have just drained the bucket.

Errors say what to do. A 4xx means this item is bad, so skip it; a 401/403 means the whole job is misconfigured, so abort; exhausted retries skip one item, but 20 in a row mean Kalshi or the network is down, so the job stops instead of marking thousands of items failed. The client also validates filter values itself, because Kalshi silently ignores bad ones and turns a typo into a full pull.

Calibration without lookahead. Kalshi overwrites a market’s close time when it closes early, so the pipeline captures the scheduled close from observations made before close. Each horizon uses only the latest candle visible at its cutoff, results are reported per anchor type, standard errors are clustered by event so ten related markets don’t count as ten samples, and edge is measured net of taker fees.
