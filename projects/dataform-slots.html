Dataform Slots Optimization

bigquery cost automation · deployed · $50K+/yr saved

Every Dataform model in the warehouse bills against BigQuery on-demand pricing by default. Some of them shouldn't. This pipeline reads seven days of job history, works out per-action whether slot reservations or on-demand is cheaper, then goes and edits the source repository itself — injecting a pre_operations block with the right SET @@reservation target and opening a pull request for a human to approve.

Confirmed against historical slot and on-demand billing across the Dataform model set. The pipeline holds that number without anyone re-running the analysis by hand — it re-evaluates every model quarterly and rewrites the routing when the answer changes.

The problem

Dataform models run as BigQuery jobs, and by default those jobs land on on-demand pricing — billed per terabyte scanned. The organisation also owns a dedicated slot reservation, billed per slot-hour. Neither model is universally cheaper. A scan-heavy job that finishes fast is cheap on-demand and expensive on slots; a long-running job that grinds through comparatively little data is the reverse.

Historical analysis of INFORMATION_SCHEMA.JOBS_BY_PROJECT showed the split runs straight through the middle of the model set. Deciding per model by hand, then keeping that decision current as data volumes drift, is not work anyone was going to do repeatedly.

The solution

BigQuery exposes routing as a session variable, so the decision can live in the source file. For an action that benefits from the reservation:

pre_operations {
  SET @@reservation = 'projects/project_id/locations/location/reservations/reservation_id';
}

And for one that should stay on on-demand compute:

pre_operations {
  SET @@reservation = 'none';
}

The pipeline's whole job is to decide which of those two statements belongs in which file, and then to put it there without breaking anything around it.

The full run path — cost evaluation through to an open pull request — is laid out under architecture.

Run path

The pipeline is append-only in spirit: it reads billing history, decides once per action, and proposes a change. Every stage above is idempotent — a repository already carrying the correct reservation produces no diff, and therefore no branch and no pull request.

Mapping a job back to a file

The hard part isn't the cost math, it's attribution. A BigQuery job record carries no pointer to the .sqlx file that produced it — by the time the query reaches the engine, Dataform has compiled it away. Paths don't survive compilation either.

The pipeline gets around this using the workflow execution labels Dataform attaches to the jobs it submits. Two labels do the work:

LabelUsed for
dataform_workflow_execution_action_id_nameResolves to the action name, which maps to the .sqlx file name on disk
dataform_repository_idIdentifies which repository to clone and modify

That pairing is what makes the loop closeable: a cost decision computed in the warehouse can be written back into the file that caused it.

Pipeline stages

  1. Cost evaluationThe orchestrator queries INFORMATION_SCHEMA.JOBS_BY_PROJECT for Dataform jobs over the trailing 7 days, filtering out state-resolution queries and cache hits so they can't skew the averages.
  2. Label extractionEach job row is joined back to its source through the Dataform workflow execution labels above.
  3. Metric calculationPer action: total slot hours, terabytes processed, on-demand cost, and slot cost.
  4. Threshold comparisonreservation_action is set to 'slots' when average slot cost is less than or equal to average on-demand cost, and 'none' otherwise. The tie goes to slots.
  5. Mapping table generationResults are written to a central BigQuery mapping table via create-or-replace, so the table is a snapshot of the most recent evaluation rather than an append log.
  6. Repository groupingpull_table reads the mapping table back and returns the actions grouped by repository, so each repo is cloned exactly once regardless of how many files it contributes.
  7. Code modificationThe worker clones, locates each target file, and hands the contents to the modifier for parsing and injection.
  8. Version controlA branch is cut and named from the Jira ticket ID plus a timestamp, changes are committed, and the branch is pushed with retries.
  9. Pull requestA POST to the Bitbucket REST API opens a PR against prd. Nothing merges automatically — a human reviews every rewrite.

Why a human stays in the loop

The pipeline has write access to production data pipelines. The design decision throughout is that it proposes and never disposes: it opens a PR, it doesn't merge one. DRY_RUN exists for the same reason — a full run can be executed end to end with the file writes replaced by unified diffs printed to the logs.

Failure posture

  • The Bitbucket token is pulled from Secret Manager at runtime and masked out of subprocess stderr before anything is logged, so a clone failure can't leak credentials into Cloud Logging.
  • Push is wrapped in retries, since transient remote failures are the common case and a failed push otherwise strands a modified working tree.
  • If the modifier returns content identical to what it read, the file is skipped entirely — runs are idempotent, and a re-run on an already-optimised repo produces no branch and no PR.
  • The Cloud Run Job has a 300 second timeout and a single retry. A run that exceeds that budget is a signal that the repo set has outgrown the current sequential design.

1 — Locating and reading the file

worker.py receives a target file name such as my_action.sqlx and walks the cloned tree recursively until it finds a match, then reads the file whole. newline="" is deliberate: it keeps the file's original line endings intact so the resulting diff contains only the intended change and not a repo-wide CRLF flip.

file_path = find_file(target_file_name, repo_dir)
# ... checks if file exists ...
with open(file_path, encoding="utf-8", newline="") as file:
    raw_content = file.read()

2 — Parsing blocks without a parser

A .sqlx file is a set of named blocks — config, js, pre_operations — each wrapped in curly braces. Those blocks routinely contain JavaScript and JSON with braces of their own, which means a regex that matches from the opening brace to the next closing brace will happily truncate a block halfway through and leave behind a syntactically broken file.

_find_blocks in dataform_modifier.py solves this in two moves.

Step A — regex finds only the header

The pattern is scoped to the block name and its first opening brace, nothing more. Multiline mode anchors it to the start of a line, so a mention of config inside a SQL comment or string can't trigger a match.

# Pattern looks for start of line, optional spaces, the block name, and the first '{'
pattern = re.compile(rf"(?m)^\s*({'|'.join(block_names)})\s*\{{")

Step B — brace counting finds the end

From the opening brace the function walks the string character by character, incrementing on { and decrementing on }. Depth returning to zero is the true end of the block, nesting included.

brace_count = 0
end_index = -1

# Manually count braces to find the true end of the block
for i in range(brace_start, len(raw_content)):
    if raw_content[i] == "{":
        brace_count += 1
    elif raw_content[i] == "}":
        brace_count -= 1

    if brace_count == 0:
        end_index = i + 1
        break

The result is a block descriptor carrying start and end offsets into the original string — enough to slice the file apart and reassemble it around a replacement.

3 — Injecting the reservation

process_sqlx_contents builds the statement SET @@reservation = '...'; and then branches on whether the file already has somewhere to put it.

Scenario A — a pre_operations block exists

The block is checked for an existing reservation assignment:

r"SET\s+@@reservation\s*=\s*['\"].*?['\"]\s*;"
  • Match found — re.sub swaps the old target for the new one in place. A model flipping from slots back to on-demand is the same code path as the reverse.
  • No match — the statement is inserted immediately after the opening brace of pre_operations, ahead of whatever else the block already does.

Either way the updated block is stitched back into the file using the offsets from _find_blocks, leaving every byte outside the block untouched:

return raw_content[: block_info["start"]] + updated_block + raw_content[block_info["end"] :]

Scenario B — no pre_operations block

A new block is generated:

new_block = f"pre_operations {{\n  {injecting_statement}\n}}"

Placement then follows the file's existing conventions. The modifier looks for config and js blocks, takes the end index of the last one, and inserts directly below it. If the file has neither, the new block is prepended to the top. The effect is that generated code lands where a person would have written it, which keeps review cheap.

4 — Diff or write

Back in the worker, the modified string is compared against the original. Identical means nothing was needed and the file is skipped. Otherwise the run branches on DRY_RUN: enabled, and difflib.unified_diff logs a terminal-readable comparison with nothing written to disk; disabled, and the file is overwritten — again with newline="" to preserve the original line endings.

with open(file_path, "w", encoding="utf-8", newline="") as file:
    file.write(modified_content)

5 — Cloning, committing, and opening the PR

Cloning uses a Bearer token passed through an inline git header rather than embedded in the URL, so the credential never becomes part of a remote string that git might echo or persist. _execute_clone_subprocess wraps the call and scrubs the token out of stderr before any of it reaches the logger.

After modification, commit_and_push sets the git identity, cuts a branch named from the Jira ticket ID, commits, and pushes upstream with retries. _create_pull_request then assembles a JSON payload and POSTs it to the Bitbucket REST API, targeting prd.

Known limitations

Tracked in FUTURE_WORK.md alongside the planned work.

  • Aliased actions can't be resolved. find_file matches the action name against file names on disk. When a Dataform action has been renamed in its config block, the action name and the file name diverge and the lookup fails. The fix is to read config blocks during the walk and build an alias-to-path map before searching — the block parser needed for it already exists.
  • Zero-margin switching. The rule currently flips to slots whenever slots are cheaper by any amount, so an action a fraction of a cent apart will churn between states across runs.
  • Cost arithmetic lives in the pipeline. On-demand and slot costs are computed in the orchestrator's SQL. Reconciling that arithmetic line-for-line with the FollowRabbit models is tracked below so both sides report the same number by construction.

Planned

  • Percentage threshold buffer. Require slots to beat on-demand by a configurable margin before switching, which kills the churn described above.
  • Cost calculation alignment. Refactor the financial logic to match the internal cost models produced by the FollowRabbit team, so the pipeline's reporting and the official projections stay in lockstep as reservation pricing changes.
  • Alias resolution. Parse config blocks to map action names to true file paths.
  • GitLab support. Generalise git_integration so clone, push, and merge-request logic work against the GitLab API ahead of the organisational migration off Bitbucket.
  • Google Chat notifications. Post an execution summary and the PR links to a Chat space on completion, so a run that opens PRs doesn't depend on someone checking Bitbucket.
  • Automatic reviewers. Assign the Advanced Analytics leads as explicit reviewers on every generated pull request.

What I'd do differently

  • Repositories are processed sequentially inside a 300 second budget. That holds at the current repo count and won't forever — fanning out one Cloud Run task per repository is the obvious next move.
  • The mapping table is create-or-replace, so each run overwrites the last. Keeping history would make it possible to see which actions oscillate, and to tune the threshold buffer against real data rather than a guess.
